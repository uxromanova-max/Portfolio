## Что это за проект

Портфолио-сайт в трёх версиях под три разных карьерных трека одного человека: **Brand Manager** (мастер-версия), **Product Manager**, **Assistant (EA/Chief of Staff)**. Версии не связаны между собой ссылками, не индексируются поисковиками и не имеют общей навигации — каждая отправляется напрямую конкретному рекрутеру под конкретную вакансию.

## Правила работы с запросами. ##
- Все запросы реализуй на прямую. Не объясняй реализацию, если нет проблем. 
- При просьбе изменить что-то на сайте - Никогда не переписывай код с нуля всего блока или сайта. Разрешается только корректировать ту чать кода которая решит проблему или задачу которая будет в запросе.
- Не надо читать весь проект при внедрении мелких правок не касающихся всей концепции. В случае если ты сомневаешься что сможешь решить задачу без пересмотра проекта, ты обязан отправить запрос на апрув этого действия.
- Каждая задача которая расходует очень большое количество токенов, выше нормы, прежде чем выполнять согласуй ее со мной и объясни есть ли альтернативные решения этой задачи с использованием меньшего количества токенов.


## Архитектурный принцип: один код, разный контент

**Компоненты общие для всех трёх версий. Разный только контент.**

- Все секции сайта (Hero, About/Why-me, Capability map, Case studies, Skills & Tools, AI & Systems, CTA) — это React-компоненты, которые не хранят текст внутри себя. Весь текст, порядок и картинки приходят из `content/brand.json` / `content/product.json` / `content/assistant.json`.
- Меняешь анимацию, отступ, стиль кнопки — правишь один компонент, это применяется сразу ко всем трём версиям.
- Меняешь текст, заголовок кейса, фото — правишь только соответствующий JSON-файл, компонент не трогаешь.
- **Не создавай отдельные копии страниц/компонентов под каждую версию.** Если кажется, что версии не "переиспользуются" — это почти всегда сигнал, что что-то нужно вынести в контент-файл, а не разветвлять код.
- Количество кейсов, пунктов capability map и т.д. может отличаться между версиями — компонент кейсов должен рендерить `caseStudies.items` как массив произвольной длины, а не ожидать фиксированное число блоков.
- Формат кейса может отличаться (`format: "standard"` — с Context/Problem/Decisions, `format: "leadership"` — как у кейса Peachy, без Context/Problem). Компонент кейса должен уметь рендерить оба формата условно, по полю `format`.
- Схема и инструкция по редактированию контента — в `content/README.md`.

## Стек

Next.js (App Router, статическая генерация где возможно) + Tailwind CSS + Framer Motion для анимаций. Деплой — Vercel.

## Производительность — обязательные правила

Сайт с богатыми анимациями всё равно должен грузиться быстро. Это не пожелание, а требование к каждому PR.

**Изображения**
- Все изображения — только через `next/image`, никогда через голый `<img>`.
- Форматы — WebP/AVIF с fallback, не JPG/PNG напрямую где можно избежать.
- Всё, что ниже первого экрана (below the fold) — `loading="lazy"`. Первый экран (Hero) — `priority`, без lazy.
- Указывать реальные `width`/`height`, чтобы не было layout shift.

**Анимации**
- Анимировать только `transform` и `opacity`. Никогда не анимировать `width`, `height`, `top`/`left`, `margin` — это вызывает reflow и тормозит на мобильных.
- Обязательно учитывать `prefers-reduced-motion` — для пользователей с этой настройкой сложные анимации отключаются или упрощаются.
- Framer Motion — точечно, на конкретных анимированных элементах, а не как глобальная обёртка всей страницы.
- Тяжёлые анимации (параллакс, сложные transition-цепочки) — грузить лениво (`dynamic import`) для секций, которые не видны при первой отрисовке.

**Шрифты**
- Subset шрифтов (только нужные символы/языки — минимум латиница, кириллица если используется в UI).
- `font-display: swap`.
- Preload только шрифт(ы), критичные для первого экрана.

**Код**
- Code-splitting по секциям — тяжёлые секции (например, что-то с canvas/WebGL, если появится) грузятся асинхронно, не в основном бандле.
- Не тащить тяжёлые библиотеки ради одной мелкой анимации — сначала проверить, можно ли сделать на чистом CSS.

**Мобильная версия**
- Не просто адаптивная вёрстка — реально урезанный по весу мобильный бандл: часть decorative-анимаций на мобильных можно упрощать или отключать, если они не несут функциональной нагрузки.
- Проверять реальный вес страницы на мобильном throttling (Slow 4G) в Lighthouse/Chrome DevTools, не только на десктопе.

**Добавление новых сторонних библиотек (визуальные эффекты, анимации, декоративные фичи)**
- Перед тем как добавлять новую JS-библиотеку под конкретный визуальный эффект (например, анимированный WebGL/3D-фон вроде Vanta.js/Three.js, сложные partical-эффекты и т.п.) — сначала оценить, можно ли добиться того же эффекта средствами, которые уже есть в проекте (чистый CSS, Framer Motion, canvas без тяжёлых зависимостей).
- Если лёгкой альтернативы нет и библиотека реально нужна — явно назвать её вес (размер в бандле) и обосновать, почему он оправдан именно для этого элемента, прежде чем добавлять в зависимости.
- Такие библиотеки подключать точечно, только на той секции, где нужен эффект (dynamic import/code-splitting), никогда глобально на весь сайт.
- Останавливать/приостанавливать анимацию, когда элемент не виден на экране (`IntersectionObserver` или аналог), не рендерить вхолостую за кадром.
- Обязательно учитывать `prefers-reduced-motion` и слабые/мобильные устройства — для них эффект отключается или заменяется на статичную/облегчённую версию.
- Не добавлять библиотеку "про запас" или потому что она красиво выглядит в чужом демо — только под реальную, согласованную задачу конкретного экрана.

**Ориентир по метрикам**
- Lighthouse Performance ≥ 90 на мобильном для каждой из трёх версий перед тем, как считать секцию/страницу готовой.
- Не сдавать секцию как "готова", если она не проверена на мобильном экране физически (не только в responsive-режиме браузера).
